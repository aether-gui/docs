# Bulk Deployment

> **Note: This feature is under active development and subject to change.** The format, behavior, and validation rules described here represent the current design direction and may evolve based on feedback and implementation experience.

Bulk deployment provides a way to deploy components across many nodes using a single CSV-style file — without interacting with the Web UI. The file combines node inventory (names, addresses, credentials) with per-node configuration overrides in one place.

This is useful for large-scale deployments where manually configuring each node through the UI is impractical, and for environments where deployments are driven by files managed in version control or generated by external tooling.

## File format

A bulk deployment file is a single text file organized into **component sections**. Each section:

- Begins with a comment line identifying the component (e.g., `# RAN`, `# 5G Core`)
- Contains a CSV header row defining the columns for that section
- Contains one row per node instance

Different sections can have different columns — the CSV structure is homogeneous within a section but varies between sections, since each component type has its own set of configurable fields.

## Row structure

Every row must include the following **connectivity fields** plus zero or more **configuration override columns**.

### Required fields

| Field | Description |
|---|---|
| `node_name` | Unique identifier for the node |
| `ip_address` | IP address used to reach the node |
| `username` | SSH username for node access |
| `password` | SSH password (or secret reference) |

### Configuration override columns

Any additional columns after the required fields are treated as configuration overrides. Column names map directly to configuration keys for the component. Only include columns for fields that need to differ from the base configuration — omitted fields retain their defaults.

## Full example

```csv
# RAN
node_name,ip_address,username,password,center_frequency,bandwidth,tx_power
gnb1,10.0.0.10,admin,admin123,3500,100,30
gnb2,10.0.0.11,admin,admin123,3600,80,25

# 5G Core
node_name,ip_address,username,password,amf_region,upf_mode
core1,10.0.1.10,admin,admin123,us-west,distributed
core2,10.0.1.11,admin,admin123,us-east,centralized
```

In this example:

- The **RAN** section deploys two gNB nodes with per-node overrides for `center_frequency`, `bandwidth`, and `tx_power`
- The **5G Core** section deploys two core nodes with per-node overrides for `amf_region` and `upf_mode`
- Each section has its own CSV header because the override columns differ by component type

## How overrides are applied

Each row in the file performs two operations:

1. **Node registration** — the node is registered (or matched to an existing node) using `node_name` and the connectivity fields
2. **Configuration override** — the override columns are applied to the component's base configuration for that node, replacing only the specified fields

Override columns that are not present in a row leave the corresponding base configuration value unchanged. This is the same partial-override behavior used by the configuration override view in the Web UI, applied on a per-row basis.

## Behavior

1. The parser scans the file for section comments (lines starting with `#` followed by a component name)
2. Each section is mapped to a known component type
3. The CSV header row immediately following the section comment defines the column layout
4. Each subsequent row is parsed according to that header until the next section comment or end of file
5. Rows are processed in order: nodes are registered, then overrides are applied

## Validation

The following checks are performed after parsing:

| Check | Scope | Behavior |
|---|---|---|
| Required fields present | Per row | `node_name`, `ip_address`, `username`, `password` must all be non-empty |
| IP address format | Per row | `ip_address` must be a valid IPv4 or IPv6 address |
| Section component mapping | Per section | The section comment must match a known component type |
| Configuration field existence | Per override column | Override column names must exist in the component's configuration schema |
| Credential format | Per row | Credentials must be in a valid format (plaintext or future secret reference syntax) |

Validation runs against the entire file before any changes are applied. If validation fails, no nodes are registered and no overrides are applied.

## Open questions

The following design decisions are not yet finalized:

- **Strict vs permissive validation** — should unknown configuration fields cause a hard failure, or produce a warning while still applying known fields?
- **Unknown field handling** — if a column name does not match any known configuration key, should the row be skipped, the column ignored, or the entire file rejected?
- **Conflict with existing state** — how should the system handle cases where a node already exists with different connectivity details, or where an override conflicts with a previously applied configuration?
- **Runtime reconfiguration** — what level of reconfiguration is supported by underlying components after initial deployment?
